# r18 实施报告：GC 模式实测，Server GC 关闭 DATAS 后重负载快 14%~31%

> **元数据** ｜ 类型: report ｜ 日期: 2026-10-09 ｜ 轮次: r18 ｜ 主题: gc-mode-measurement-and-datas-off
> 涉及 git 节点: `91fedba629`（r17 对比表，工作树基线）/ 本轮提交
> 数据来源: 8 个配对批次（AB86~AB94，每批 23 或 7 负载 × 15 组交替配对，`--no-gc-env`）；4 个 AOT 产品变体；24 夹具 + 12 关系夹具产物逐字节比对

## 0. 本轮结论

**对当前项目，性能最强的 GC 配置是 Server GC 且关闭 DATAS**（`ServerGarbageCollection=true` + `GarbageCollectionAdaptationMode=0`）。相对当前出厂配置（.NET 9 起默认开启的 Server GC + DATAS）：

| 负载组 | 耗时变化（B ÷ A，两次全负载批次一致） |
| --- | --- |
| medium 族 4 项 + declarations | **−18% ~ −32%** |
| huge-file、medium-checkers-1 | **−12% ~ −14%** |
| project-references 6 项 | −4% ~ −11% |
| tiny-files 族 4 项 | **+2% ~ +9%（变慢）** |
| version/help/empty 等启动项 | 噪声内 |

代价是峰值内存：巨文件 254 → 376 MiB（+48%），tiny-files 族 61 → 186 MiB（+195%）；medium 族与工程引用持平。

本轮已把该配置落入产品（`pkgs/r18/lib/tsc.exe` sha256 `a2742351485…`，29,779,968 B，0 警告），并经 AB94 确认与实验变体行为一致、24 + 12 个夹具产物逐字节不变。

## 1. 机制：四种模式的取舍

.NET 11 的 GC 选择分两层：主形态（Workstation 默认 / Server）加子形态（后台并发默认 / 非并发），.NET 9 起 DATAS 默认开启。四种实测变体：

| 变体 | 配置 | 堆数 | 机制要点 |
| --- | --- | --- | --- |
| **A（当前出厂）** | Server + 后台 + DATAS 开 | 启动 1 个，按需增长 | DATAS 按长寿命数据规模约束 gen0 预算，需要时做全压缩 GC |
| **B（本轮落地）** | Server + 后台 + DATAS 关 | 每逻辑核一个 | 经典 Server GC，按吞吐开堆，可积极增长 |
| **C** | Workstation + 后台 | 1 个 + 1 个后台 GC 线程 | 低内存低延迟，收集能力受单线程限制 |
| **D** | Workstation + 非并发 | 1 个 | 无后台线程，gen2 阻塞式收集 |

**DATAS 为什么伤到这个项目**：DATAS 启动时只有一个堆，靠分配等待信号按需增加堆数（运行时文档明确把"进程启动后多线程立即大量分配"列为吞吐受损的过渡情形）。tsc 的检查阶段正是这个形态：并行检查器在约 150 ms 内分配 870 MB，堆数还没长起来分配线程就先等待；DATAS 的全压缩 GC 又叠加暂停。微软自家基准（48 核 Linux，TechEmpower）显示 DATAS 用 2~3% 吞吐换 80% 工作集，那是对常驻服务有意义；对 0.1~1 秒就退出的编译器，内存节省随进程退出清零，吞吐代价每次运行都付。

**Workstation 为什么输给 B**：C/D 在 medium 族比 A 快 5~19%（开销低），但巨文件慢 17~28%（32K 对象字面量的并行分配爆发，单堆单 GC 线程吸收不了）；与 B 正面交手（AB90/AB91）也是 B 在巨文件快 27~32%、medium 族再快 8~9%。

## 2. 实验矩阵与批次有效性

| 批次 | 对比 | 负载数 | 控制项 p95rel | 控制项 medianRatio（CI） | 结论 |
| --- | --- | ---: | ---: | --- | --- |
| AB86 | B vs A（DATAS 关 vs 开） | 7 | 30.7% | 1.006（[0.928, 1.106]） | B 在 5 个重负载快 15~44% |
| AB89 | A vs B（反向复核） | 7 | 100.6% | 1.002（[0.950, 1.053]） | 同上，方向一致 |
| AB87 | A vs C（Server vs Workstation 后台） | 7 | 30.1% | 0.973（[0.834, 1.090]） | C 在 medium 族快 5~7%，巨文件慢 28% |
| AB88 | A vs D（Server vs Workstation 非并发） | 7 | 71.1% | 1.120（[0.919, 1.262]） | D 在 medium 族快 12~19%，巨文件慢 17% |
| AB90 | C vs B | 7 | 5.3% | 0.998（[0.969, 1.029]） | B 全面快于 C（巨文件快 32%） |
| AB91 | D vs B | 7 | 20.3% | 0.995 | B 全面快于 D（巨文件快 27%） |
| **AB92** | **A vs B 全负载** | 23 | 110.3% | 1.005（[0.958, 1.109]） | **B 在 16 项显著更快，3 项更慢** |

所有批次控制项 CI 均含 1.0（槽位无系统偏置）；部分批次 p95rel 偏高（最高 110%）来自本机同时运行的其他进程，控制项中位数无偏，且关键结论经 2~4 个独立批次同向确认。每批内部都做了产物逐字节断言（GC 模式不改变编译器输出，24 + 12 夹具另在 r17 与 r18 产品间全量比对通过）。

## 5. 落地内容与验证

`TypeScript.CommandLine.csproj`：`ServerGarbageCollection` 与 `ConcurrentGarbageCollection` 保持不变，新增 `GarbageCollectionAdaptationMode=0`，并移除显式设置 `System.GC.DynamicAdaptationMode=1` 的 `RuntimeHostConfigurationOption` 项（该项与属性互相矛盾，实测属性生效，但保留会造成误导）。注释段同步改写，记录本轮实测数据，并保留当年"固定 gen0 预算不可取"的历史结论。

| 门禁 | 结果 |
| --- | --- |
| 构建 | AOT 产品形态 0 警告 / 0 错误（`pkgs/r18/lib/tsc.exe` sha256 `a2742351485…`，29,779,968 B） |
| 行为一致性（AB94） | r18 与实验变体 B 在 7 个负载上全部噪声内（r18/B 0.967~1.051） |
| 逐字节一致 | r17 与 r18 产品间：18 合成形状 + 5 staged 负载（1,882 产物）+ 巨文件 + 12 关系夹具，全部一致 |
| safety 套件 | 未重跑：本轮只改命令行项目的 GC 配置，编译器库源码零改动，测试程序集不受影响（r17 轮的 90/95 结果继续有效） |
| 环境变量鲁棒性 | 实测 `DOTNET_gcServer` / `DOTNET_GCDynamicAdaptationMode` 环境变量对该 AOT 产品无可测影响（巨文件 3+3 次交错运行无一致差异），GC 形态由编译期决定，harness 的 `--no-gc-env` 仅为排除干扰 |

**历史注释修正说明**：当年启用 DATAS 的决策记录在 csproj 注释里，依据是"固定 gen0 预算的 Workstation GC 拖慢短负载 3~8%，DATAS 消除了这些回退"。该对比漏掉了"Server GC 无 DATAS 无固定预算"这一档，本轮补上后结论反转：该档比 DATAS 更快，且无需任何固定预算。
