## 0. 本轮结论

**关系引擎的缓存机制是健康的，不需要改动缓存策略。** r14 报告建议"先测顶层缓存命中率与重复比较率再决定是否动缓存"，本轮测完的答案是：

| 指标 | 实测 | 读法 |
| --- | ---: | --- |
| 顶层查询数 | 43,459 | 到达关系引擎主体的查询（已过 SimpleAsync 等廉价判定） |
| 顶层缓存探测覆盖面 | 11,378（26.2%） | 仅双侧 ObjectType 的查询探测顶层缓存 |
| 顶层缓存命中率（对探测） | 5,996 / 11,378 = **52.7%** | 探测到的对里过半已有结果 |
| 会话内进入次数 | 65,404 | 递归比较总进入 |
| 会话内缓存命中率 | 25,470 / 65,404 = **38.9%** | 近四成的递归比较被缓存挡掉 |
| 真正结构化比较 | 37,048（56.6%） | 跑完整属性/签名/索引比较 |
| 键构造总数 | 77,529 | — |
| 缓存新增条目 | 35,647 | 不同键的总数（跨关系种类与会话累加） |
| **重复键构造率** | 1 − 35,647/77,529 = **54.0%** | 过半键构造命中已存在的键 |
| WithoutErrors 包装 | 32,541 次 | 占会话进入的 49.8% |
| Failed 缓存重算（recheck） | **10 次** | reportErrors 时因要重新生成解释而绕过缓存 |
| 复杂度溢出 | **0 次** | 该负载不触发 Overflow |

两条先验假设被证伪（§3）。重复键构造的 54% 里绝大部分是零堆分配的 struct 构造，没有分配收益空间；缓存策略的任何改动（扩大顶层覆盖面、给泛型键接交替相等比较器）都是高风险低收益。

## 1. 为什么测这些

r14 的归因结论是关系引擎占真实工程分配的 44.7% 但分布弥散，单次比较成本里没有结构性缺陷，因此"下一步若要动关系引擎，杠杆不在单次比较的成本，而在比较次数"，并列了两个待量化项：顶层结果缓存命中率、同一对类型的重复比较率。本轮用计数器把两者测出来。

口径说明：计数器经 `CompilationCapture.Current` 累加（跨并行检查器求和），与 r15 同负载同构建形态。负载含 11 行 TS7006 诊断（C# 移植版既有推断差异，r15 已记录），不影响计数。

## 2. 缓存机制的两层结构与测量点

| 层 | 位置 | 键的来源 | 命中后的动作 |
| --- | --- | --- | --- |
| 顶层探测 | `TypeRelations.RelatedCoreAsync` | 未规范化的 (source, target) | 直接返回布尔，不租会话 |
| 会话内 | `RelationSession.RecursiveCoreAsync` | 规范化后的 (source, target) | 直接返回 Ternary |

顶层探测只对双侧 `ObjectType` 开放（第 147 行的条件）。这不是遗漏而是约束：`CompareCoreInnerAsync` 在进入会话后才做 `normalization.GetAsync`，联合与交叉类型的规范化会改变类型（联合归约、交叉展开），顶层用未规范化类型构造的键与会话内的键对不上；普通对象类型的规范化是恒等，所以键一致。要把顶层探测扩展到联合类型，必须先把规范化提到顶层，而那可能比省下的缓存探测更贵。

## 3. 两条被证伪的假设

**假设一：`WithoutErrorsAsync` / `CompareContinuingAsync` 会绕过部分缓存（r14 报告的表述）。** 证伪。这两个包装只做 `suppressed++` 后照常走 `CompareAsync` → `RelatedAsync` → `session.RecursiveAsync`，会话缓存对它们完全有效。实测 32,541 次包装调用，而 reportErrors 时因缓存条目标是 Failed 需要重新生成解释才绕过缓存的情形只有 **10 次**（0.03%）。代码上对应 `RecursiveCoreAsync` 的 recheck 分支：`cached != 0 && reportErrors && Failed && !Overflow` 时不返回缓存值。该分支为诊断正确性而存在（要重新产出错误解释链），但实测几乎不触发。

**假设二：54% 的重复键构造意味着可观的重复比较开销。** 证伪。`RelationKeys.CreateAsync` 对非泛型对直接返回普通两类型键：`RelationKey` 是带缓存哈希的 readonly struct，**不分配堆**，重复构造的成本只是 `HashCode.Combine` 的 CPU 时间。分配路径（`List<Part>` + `Dictionary<Type,int>` + `ToArray`）只在两侧之一是泛型类型引用时进入，r14 实测该负载只有 1,218 次，占 77,529 次键构造的 1.6%。也就是说 54% 的重复率里约 98% 是零分配重复，拿它做"减少重复比较"的优化，收益上限是百分之几的 CPU 时间，且要改动缓存键结构（r14 已评估：接 `IAlternateEqualityComparer` 需改约 10 个字典创建点）。

## 4. 分布读数

**会话内的 65,404 次进入**：38.9% 缓存命中、4.4% maybe（递归循环的 Maybe 短路）、56.6% 真正结构化比较、0 溢出。平均每个进入会话的顶层查询引发 1.75 次会话进入（65,404 / 37,463），即嵌套比较只占 0.75 次每查询，联合分发的重复比较大部分被缓存挡住。

**顶层 32,081 次非 ObjectType 对查询**（73.8%）不探测缓存直接进会话。这些查询每次要租会话、建 `RelationOperation`、走 `CompleteAsync`。r14 实测 `RelationOperation` 分配 49,069 次约 3.0 MB（0.5%），且该对象持有可变状态（`Explanation`、`suppressed`），池化风险大于收益，本轮不复测。

**37,048 次结构化比较**是 relationCompare 418 MB 的主体，平均每次约 11.6 KB。r10 的同形快路径与 r14 的归因已经覆盖了其中可识别的高频形态（匿名同形对象直返、签名与属性段是透传）。要进一步减少这 37,048 次，需要识别"哪些比较对在重复出现且本可避免"，那要求每个顶层查询内的去重集合，成本高于收益。

## 5. 对下一步的判断

关系引擎的三个可能杠杆都测过了，结论一致：**这个引擎已经在有效工作，剩余大头是合法工作本体**。

| 杠杆 | 实测 | 判断 |
| --- | --- | --- |
| 提高顶层缓存命中率 | 覆盖面 26.2% 是规范化约束，非遗漏；扩展需先规范化，可能更贵 | 不做 |
| 减少重复比较 | 54% 重复键构造中 98% 零堆分配；CPU 侧收益 <1% | 不做 |
| 缓存键结构改动 | r14 评估收益 0.3%，改动面 10 个字典创建点 | 不做 |

下一轮的方向建议离开关系引擎。剩余未归因的大块（r15 口径，真实工程 959 MB）：成员表构建 `resolveMembers` + `setMembers` 245 MB（25.5%）、类型引用解析 `typeReference` 41 MB、`symInstantiated` 28 MB。前者是合法工作但占比最大，值得用 r15 的内层探针方法拆一层，确认里面是否藏着与 r15 同族的"每次调用一个容器"缺陷。
