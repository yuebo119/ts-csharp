## 2. 诊断过程：为什么上一轮的判断错了

r45 只处理「恰好一个逆序点」的情况，理由是 r41/r45 的探针报告「155 of 172 大 union 恰好一个逆序」。这一轮的分段计时推翻了这个理解：

| 阶段 | 耗时（proto.ts） | 比较次数（全工程） |
| --- | ---: | ---: |
| `flatten` | 2.3 ms | 未统计 |
| `descentScan` | 10.5 ms | 153,156 |
| `sortOrMerge` | 143.3 ms | 618,116 |

扫描只占 7%，而 `sortOrMerge` 占 93%。既然 r45 已让 155/172 走归并，为什么归并段还有 618k 次比较？

逆序点直方图给出了答案（按元素数计）：

| 逆序点数 | 元素数 |
| ---: | ---: |
| 0 | 59,844 |
| 1 | 53,683 |
| 2 | 4,282 |
| 3 | 1,634 |
| 4 | 600 |
| 5~11 | 765 |
| 12 | 3,080 |
| 13~21 | 1,180 |
| 更多 | 余量 |

**42,000 个元素落在 2~21 个逆序点的列表里**，它们全部走 `types.Sort`，付出 `n log n` 次比较。r45 的探针只统计了「大 union（N≥129）」的分布，忽略了这些中等规模的多段列表。

这正是 tsrs 的 `merge_ascending_runs` 处理的一般情形：不看逆序点数，直接把列表看作若干升序段，自底向上归并。代价是每元素每轮一次比较，总比较数约为 `n × ceil(log2 k)`（k 为段数），而 introsort 是 `n log n`。

## 3. 实现

`TypeAlgebra.AddUnionTypes` 的排序段：

1. 扫描一遍记录全部逆序点位置到 `runs`（不再提前 break）；
2. 若 `runs.Count > 1`，调用 `MergeRuns`；
3. `MergeRuns` 把 `runs` 当作段起点表，末尾追加 `count` 作为哨兵，然后逐轮两两归并：每轮合并相邻两段（末段单独保留），交替写入 `mergeScratch` 与原列表，直到只剩一段；
4. 若最终结果在 `mergeScratch` 里，拷回原列表。

缓冲区 `runs`、`nextRuns`、`mergeScratch` 都是 `TypeAlgebra` 的实例字段，跨调用复用，不产生每调用分配。归并循环用 `order.Compare(a, b) <= 0` 保持与 `Sort` 相同的稳定顺序。

正确性依据与 r45 相同：比较器是「只有相同类型才比较相等」的全序，因此任何正确的归并/排序都产出同一序列；重复成员在随后的去重遍历里合并。

## 4. 正确性验证

断言从 143 增至 **153**，新增 10 个覆盖多段归并：

- 既有：64 个字面量逐个相邻交换（单点逆序）、两处交换（2 处逆序）；
- 新增：按 k = 3、5、8、13、21 旋转构造 k 段升序列表，每个都断言归并结果与升序基线**对象相同**且成员序列相同。

旋转是关键构造：把升序列表左旋 k 位，得到恰好 k 段升序的列表，无需依赖具体比较结果就能构造任意段数。

**变异验证**（两次）：

1. 去掉「结果在 scratch 时拷回原列表」的分支 → 第 16 断言失败。这证明测试覆盖了缓冲区翻转。
2. 把合并对的段边界从 `target.Count` 改成 `mid`（只影响 k≥3 的路径）→ 测试失败。这证明新增的旋转用例真的覆盖了多段归并，不是空转。

## 6. 测量方法的两处修正

**fixture 源目录污染。** 全量态批次跑出 CPU 1,594（真全量约 5,500），查明是源目录残留 `tsconfig.tsbuildinfo` 被配对驱动 `cpSync` 带走，实际跑成了增量恢复态。清理后重测才得到 832 MiB / CPU 5,625 的真实全量读数。此后每轮跑前都清理 `dist/` 与两个 tsbuildinfo。

**探针的增量 bug。** 首版分段计时把 `TypeOrder.CompareCount` 的累计值当成了本次增量，读出 7.8e9 次比较。改为记录进入前的快照再做差，才得到 618,116 这个可用数字。这类探针算术错误会直接导致错误结论，需要在报告里记录以免复现。

## 7. 为什么这一轮能过端到端而 r45 不能

r45 的检查相位降 4.2%，理论上限 `16% × 48% × 53% ≈ 4%`，落在本机 ±5~10% 分辨率内。

本轮检查相位降 13.1%，理论上限约 `51% × 48% × 53% ≈ 13%`，实测 5.7~7.7%，已经超出分辨率。这也解释了 r39-L3a 的「checkPool −17% 端到端 1.006」为什么相反：那次收益被 emit 尾部的增长吃掉，而本轮没有触碰调度与 emit，收益如实传导。
