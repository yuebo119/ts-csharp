### 0.3 检查阶段按节点种类归因（r04 已提交的插桩）

分配 179.8 MB：**`VariableDeclaration` 157.0 MB（88%）**、PropertySignature 11.2 MB、VariableStatement 0.4 MB。
含义：每个变量声明的**类型解析 + 初始化器检查**（匿名对象类型构造 + 可赋值性关系）约 9.6 KB。Types 82,350 → 179.8 MB ÷ 82,350 = **2.18 KB/类型**。

### 0.4 并行结构：巨文件上文件级并行完全失效

- r03 已实现**文件级**并行发射；但 `huge-file` 是**单个 1.6 MB 文件**（16,384 条顶层语句）→ 该负载上并行度 = 1，emit 685 ms 全串行。
- `--checkers N` 对**双方**都生效，故 checkers 族是同类对比：C# 并行扩展 **1.70×**（280.8 → 165.6 ms），Go 仅 **1.18×**（96.2 → 81.2 ms）。**C# 的并行扩展其实优于 Go**，问题在单线程绝对性能。

### 0.5 启动地板（r04 已测）

`--version` 整进程 ~54 ms，其中 **Main 内仅 2.9–3.9 ms**（93% 在 Main 之前：运行时/AOT 镜像初始化）。因此小负载比值里含 ~55 ms（C#）vs ~45 ms（Go）的固定成本：

| 负载 | 报告比值 | 扣除启动后的计算比 |
| --- | ---: | ---: |
| medium | 2.04× | ~3.06× |
| huge-file | 3.33× | ~3.61× |

## 2. P0：单文件内分段并行发射（最高杠杆）

### 2.1 依据

- emit 占与 Go 差距的 **62%**（522 ms / 847 ms）；
- `huge-file` 单文件使 r03 的文件级并行**零收益**；
- Go 单文件 emit 仅 163 ms（我们 685 ms，4.20×）→ 即使不并行，单线程也有 4× 空间；并行可再叠加。

### 2.2 设计

```
顶层语句列表（16,384 条）
   ├─ 切分：按语句边界切成 K 段（K = min(ProcessorCount, 32)，段内字节量均衡）
   ├─ 每段独立执行：变换（transform）+ 打印（print）→ 写入各自缓冲
   └─ 按序拼接缓冲 → 与串行结果逐字节一致
```

**关键约束与处理**：

| 约束 | 处理 |
| --- | --- |
| 输出顺序 | 段缓冲按索引拼接，不依赖完成顺序 |
| 源映射 / 注释位置 | 仅在 `sourceMap` 关闭且段边界落在顶层语句时启用；否则回退串行 |
| 生成名（`generatedNames`）与 helpers 集合 | 先做一遍**轻量预扫描**（只走顶层语句收集 helpers/名字），再并行打印；或每段收集后按序合并（helper 输出位置在文件头，天然可合并） |
| `EmitContext` 共享状态 | 每段独立 `EmitContext` 视图 + 独立 `SyntaxPrinter` 状态（printer 已是每文件实例）；`originals` 映射按段局部 |
| 缩进/换行上下文 | 顶层语句起始缩进固定（0），段首状态可静态推导 |
| 回退 | `TSHARP_EMIT_SEGMENTS=1` 或 `sourceMap` 打开时走原串行路径 |

### 2.3 预期与验证

- 预期：emit 685 → 250–350 ms（4–8 段有效扩展 2–2.7×）；巨文件 1.173 → 0.78–0.86 s。
- 验证：harness 逐字节一致门禁（23 负载 × 15 对）+ 分段开关的配对 A/B（同二进制、同 GC），并要求 `TSHARP_EMIT_SEGMENTS=1` 与串行结果**字节相同**。

## 3. P1：检查阶段定点消除（179.8 MB / 295 ms）

### 3.1 下一步插桩（前置条件）

现有归因只到**节点种类**（`VariableDeclaration` 157 MB）。下沉一层到**方法级**，复用同一模式：

```
GetTypeFromTypeNode / GetTypeOfExpression / IsRelatedTo / GetPropertiesOfType / Widen
```

并计数**关系缓存条目数**（source,target 对数）与对象类型成员表构造次数。

### 3.2 已见候选（按预期收益排序）

| 候选 | 位置 | 预期 |
| --- | --- | --- |
| 关系缓存条目结构体化 | `Checking/TypeRelations.cs`（`Dictionary<Type, Dictionary<Type, …>>` 双层字典节点） | 每对 (source,target) 省一个字典节点；若条目数 10 万级，可省 10–20 MB |
| 对象类型成员表构造 | `BindingTypes.cs:309`、`BindingPatterns.cs:90,189`、`StructuredMembers.cs:330`（`members.Values.Order(...).ToArray()`：每次排序 + 数组） | 已排序时跳过排序；2 属性类型省 1 数组 + 1 迭代器 |
| 空集合延迟分配 | `AnonymousType` 的 `CallSignatures`/`ConstructSignatures`/`IndexInfos`/`ResolvedBaseTypes` | 每类型省 2–4 个空集合 |
| 属性查找缓存 | `GetPropertyOfType` 每次构造字典？ | 缓存或复用符号表视图 |

目标：179.8 → ~90 MB，295 → 200–220 ms。

## 4. P2：变换阶段——先按变换器归因，再消除每语句重建

### 4.1 依据

`VariableStatement` 33.5 MB（2.05 KB/语句）、`VariableDeclaration` 33.2 MB（2.03 KB/声明）、`SourceFile` 31.6 MB，合计 80%。`VisitListAsync` 已 copy-on-write，故开销在**每语句的节点重建 + 变量环境操作**。

### 4.2 下一步插桩

把归因帧从"节点种类"扩展为**变换器 × 节点种类**（`Context.PushTransformAllocationFrame(transformerName)`），回答：这 98.3 MB 属于哪个变换器（类型擦除？声明发射？模块转换？）。

### 4.3 候选

| 候选 | 说明 |
| --- | --- |
| 未变更子树共享 | 若 `VisitChildrenAsync` 发现所有子节点引用未变且本变换器未要求改动，直接返回原节点（省新节点 + 修饰符数组 + 子列表容器） |
| 变量环境操作降本 | `StartVariableEnvironment`/`MergeEnvironment` 每语句一次；改为仅在语句真正引入变量时启用 |
| 修饰符/关键字容器复用 | `ExportKeyword` 0.5 MB、`StringKeyword` 0.6 MB 等小种类合计仍可观 |

## 7. 方法论修正（本轮新增两条）

1. **compute-only 对比**：报告同时给出"报告比值"与"扣除启动（C# 55 ms / Go 45 ms）后的计算比"，避免小负载被固定成本主导（medium 2.04× vs 计算 3.06×）。
2. **归因帧必须满足两条不变式**，否则数据无效（本轮踩过）：
   - 子帧增量必须回传父帧（否则总和 = 树深 × 阶段量；本轮曾得 295 MB vs 阶段 124 MB）；
   - 帧只在所属阶段内计数（`Measure("transform")` 期间），否则跨阶段重复记账。
