## 1. 结论

r53 用探针证明 emit 相位墙钟等于「最重属主 checker 的负载」加一段阻塞尾巴，并实现了按属主派发（阻塞工时 365~395ms → 0.0ms），但当时以端到端读数不可判为由搁置。本轮补齐了两件事后发布：

1. **相位级配对证据**：`phase:emitTotal`（本轮新增的永久相位作用域）在同一二进制两臂交替的 30 对上，owner 臂中位 **0.2120s** 对 queue 臂 **0.2380s**，比值 **1.1226，CI [1.022, 1.407]**，**区间排除 1.0**。相位墙钟的逐次噪声远小于整进程墙钟，这是 r53 缺的那层证据（当时只有两次非配对读数 0.208/0.208 对 0.182/0.193）。
2. **端到端如实分层报告**：干净批次（无诊断旗标）40 对 1.0265 CI [0.978, 1.049]、60 对 1.0257 CI [0.993, 1.087]，**区间含 1.0**；同代码 noemit 对照批在 20 对上自身读出 2.4% 伪差（0.9764 CI [0.942, 1.016]），说明 2~4% 落在这台机器的分辨率内。因此本报告只声明「相位 −12.3%」，**不声明端到端收益**。

判据口径（本轮开始前定）：相位级 CI 排除 1.0 且六项门禁全过则发布；否则维持 r53 的搁置。

## 2. 改动（3 处，44 行）

| 文件 | 改动 | 为什么 |

## 7. 结构性推论：check 与 emit 共享同一关键属主

本轮顺带把「check → emit 流水线化」这条候选一并算清了，结论是**它在本负载上恒等**：

- 检查期分区负载（r52 实测，8 分区）：0.401 / 0.337 / 0.305 / 0.233 / 0.222 / 0.184 / 0.176 / 0.174 s，最重是 partition#1（含 `proto.ts`）。
- 发射期属主负载（r53 实测）：176.9 / 155.8 / 117.9 / 105.1 / 93.5 / 92.6 / 88.2 / 68.1 ms，最重也是属主 1。
- 现状关键路径 = max(check) + max(emit) = 0.401 + 0.177 = **0.578 s**；流水线形态 = max(check+emit) = 0.401 + 0.177 = **0.578 s**（属主 1 在两相位都最重），逐项相加后各属主分别为 0.578 / 0.493 / 0.423 / 0.338 / 0.316 / 0.267 / 0.264 / 0.252 s，最大者仍是属主 1。

这解释了 r39-L3-a「checkPool −17% 而端到端 1.006」为何不是 emit 尾部吃掉的偶然，而是结构性必然：**同一个最重属主同时钉住两个相位**，因此任何只改「相位如何排列」的方案都不改变关键路径。要动只能减少该属主自身的检查负载或其文件的发射工作量。

## 8. 附带否定与观察

- **启动地板是环境性的，不是 .NET 基座差**：本机 `--version` 最小耗时 C# 90ms、Go 80ms，而原生 `cmd.exe /c echo` 61ms、`where.exe` 131ms——进程创建地板本身就在 60~130ms。r30 记录的「x1.87 基座差」在 `--version` 口径下不成立（比值约 1.1），该 11%~13% 的墙钟占比对所有二进制同等，不是代码目标。
- **消融陷阱**：`-p tsconfig.json --declaration false` 会触发 `TS6304`（composite 工程不得关闭声明发射），随后检查相位被整体跳过（Check time 0.000s）却仍然发射——该形态不能用于 print 的 JS/声明侧分解，本轮弃用。该配置错误下的行为（报错但继续发射）与参考实现是否一致未查证，留给后续会话。
- **打印侧量级**（仅用合法读数）：full 运行 `Print time (summed) 0.694~0.749s` 对 `Transform time (summed) 0.205~0.210s`，输出总量 7.39 MB（6.74 MB JS + 0.65 MB 声明）；`--emitDeclarationOnly` 单跑：声明侧 print summed 0.248~0.378s / 0.65 MB。发射成本以 JS 打印为主。

- 逐次噪声：相位墙钟逐次波动远小于整进程墙钟（30 对相位 CI 宽 1.022~1.407，端到端 CI 0.983~1.066 且含 1.0）；同代码对照批给出 2.4% 的伪差地板。
- 编译类命令直接取退出码（`| grep | head` 会把失败读成 exit 0，本轮前一轮已记）。

## 10. 剩余空间

- **检查相位（0.52s / 47%）**：最大块仍是关系引擎族，受 r27 表 3 约束；且本轮第 7 节证明关键路径被 partition#1（`proto.ts` 所在分区）单点钉住，减少分区数或加 checker 都动不了它。
- **emit 相位（0.20s / 19%）**：本轮已拿走调度侧的确定性收益（12.3%）；再往下的上限是 max(最大单文件 ~139ms, sumWork/8) ≈ 139ms，即调度轴整体 ≤3%，更深只能削每文件工作量（r35 W3 家族，真实工程 ≤3%）。
- **Program（0.17s / 17%）**：余量为串行发布/应用循环，量级 ≤4%。
- **启动/进程创建（60~130ms）**：环境性，非代码目标。
- 结论同 r43/r53：本仓剩余空间都在「必要工作的常数」上，且多数低于本机分辨率；下一步的杠杆是**减工作量的架构级改动**（例如声明发射的复用与裁剪、单文件检查的切分设计），而不是调度、缓存或相位排列。
