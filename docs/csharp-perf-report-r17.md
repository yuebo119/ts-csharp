## 1. 成员表构建的帧层级（真实工程，CoreCLR 诊断构建，进程级总分配 879 MB）

| 帧 | MiB | 占 resolveMembers | 说明 |
| --- | ---: | ---: | --- |
| `resolveMembers` | 201.3 | 100% | 成员解析顶层 |
| `memObject` | 154.7 | 76.9% | 引用/接口路径（含实例化与基类） |
| `memBases` | 88.7 | 44.1% | 基类循环 |
| `memInstantiate` | 32.9 | 16.3% | 泛型实例化（表/签名/索引） |
| `memAnonymous` | 36.3 | 18.0% | 匿名对象与类型字面量 |
| `memMapped` | 9.4 | 4.7% | 映射类型 |
| `memDeclared` | 3.6 | 1.8% | 声明成员表（有缓存） |
| `memUnionIntersection` | 0.9 | 0.4% | 联合/交叉成员 |
| `setMembers`（独立帧） | 41.7 | — | 成员表落盘（两个 List + 排序 + 合并数组） |

读法：帧是包含式的。`memBases` 88.7 MB 的构成经计数器定量：基类循环迭代 6,925 次，索引合并只涉及 2,011 个元素、签名合并 123 个元素（几乎全走 `Concatenate` 的零分配快路径）。也就是说 memBases 的 97% 以上是 `InstantiateAsync`（基类型实例化）与 `host.PropertiesAsync`/`SignaturesAsync`（递归触发基类型成员解析）的透传，循环自身的容器分配不足 3%。计数器还测得 `SetCoreAsync` 累计处理 304,657 个成员（约 2 万次成员表落盘），其两个 `List<Symbol>` 与合并数组是"每成员表一次"的合法分配。

**结论：这个区块没有 r15 那类"每次调用一个容器"的结构性缺陷。** 大头是泛型实例化（memInstantiate 32.9 MB，每个实例化引用一次）与递归成员解析（合法工作本体）。

## 2. 落地内容：基类索引合并去掉 LINQ

`ObjectAsync` 的基类循环里，每处理一个基类就把继承来的索引签名按 KeyType 去重后合并：

```csharp
indexes = Array.AsReadOnly<IndexInfo>(
    [.. indexes, .. inheritedIndexes.Where(next => !indexes.Any(old => old.KeyType == next.KeyType))]);
```

每次迭代分配：`Where` 枚举器、每个继承条目一个 `Any` 枚举器、一个新的合并数组。改为一次分配的 List 加嵌套扫描（先追加旧列表，再逐个判断 KeyType 是否重复），语义逐字等价：原谓词在合并前的旧 `indexes` 上判断，新实现的内循环同样只扫旧列表；顺序保持"旧的有先、继承的追加"。

**效果**（CoreCLR 诊断构建）：`memBases` 帧 89,996,496 → 88,730,720 B（−1.27 MB，−1.4%），`memObject` 帧 −1.63 MB，`resolveMembers` 帧 −1.65 MB。

**评估后放弃的第二处**：`SetCoreAsync` 的两个 `List<Symbol>` 无容量预设，增长链有中间数组垃圾。但精确容量需要预知 declared/inherited 分流比例（class 成员表偏 declared、匿名表偏 inherited），满额预设会在错配情形白分配约等于省下的量，引入猜测性容量常数只换到 0.1% 量级的收益，放弃。
