## 2. 分配对比（MiB，确定性指标）

分配是确定性指标（同二进制重复测量差 ≤0.03 MB 量级），可比绝对值和跨会话；这与峰值内存不同（见 §2.3）。

### 2.1 三个节点

| 节点 | 真实工程 291 文件 CLR 总分配 | 相对 Go | 测量 |
| --- | ---: | ---: | --- |
| Go 参考基准 | ~155 MiB（GOGC=off 提交峰值） | 1× | r15 口径 |
| **C# 优化前基准（naot-svr）** | **866.0 MB**（825.8 MiB；两次 866,003,824 / 865,896,336） | x5.3 | 本轮 |

| 轮次 | 节点 | 总分配 | 相对上一节点 |

同一二进制同一夹具的峰值 RSS 在不同会话间相差可达 2.3 倍（DATAS 堆预算适应机器内存状态 + 操作系统工作集修剪），r17 表曾据此得出"计算型负载内存反超 Go"的结论，已在 r18 表更正为不成立。本表不重复内存对比以避免再次误读；如需内存口径，须在同一批次内重新采集。

## 4. 被实测否定或明确不做的方向（防止重探）

| 方向 | 实测结论 |
| --- | --- |
| `checkerRelated` 42 MiB 的 normalization/Simple/Weak 分解 | 三项合计 0.5 MB；主体是关系会话递归调度本体（r22） |
| 大栈专用检查器线程 | 栈守卫 874,660 次调用零让出，默认 1 MB 与 64 MB 栈结果相同，+0.33 MB（r23，已回滚） |
| 同步化重写的分配收益（−100~200 MB） | 异步状态机实测 **0 字节/次调用**（r24） |
| 同步化重写的墙钟收益（5~15%） | 每调用 2.0~2.3 ns；热帧计数 2,220,665 得 0.22%，外推 1,000 万次得 1.0%（r24） |
| S 层（`RelationOperation` 池化等） | 上限约 11 MB（1.3%），低于方案自身 10% 门槛（r22 决策点） |
| 跨 checker 链接唯一化 | 上限约 10 MB（1.2%），需共享每 checker 可变表（r22 P3 评估） |
| AST 结构体 arena 重写 | 节点尺寸已与 Go 相当（C# `IdentifierNode` ~80 B vs Go ~72 B） |
| AVX-512 / 裁剪开关 / 完整 LINQ | r20 三批实测零收益或更差 |
| 存储身份哈希 / 打印器 `Part[]` / 实参位置记忆化 | 三个历史假设已分别被实测否掉 |

## 5. 相对 Go 的差距构成（r23 口径）

| 维度 | 数据 | 归因 |
| --- | --- | --- |
| 单检查器重负载 | medium-checkers-1 **x2.06**（Go@400 x2.24），仍是 23 项最大差距 | 单 checker 串行时检查器本体最重 |
| 巨文件 | x1.45 | 单文件 32K 对象字面量；并行 8 checker 时收窄到 x1.27 |
| 工程引用族 | x1.35~x1.54 | 多项目增量调度 |
| 轻负载启动 | x1.18~1.27（Go@400） | 约 55 ms 的 Main 之前启动地板，占轻负载绝对耗时 40%~85%，无代码级杠杆（r13 定论） |
| host-paths | x1.86 | 该负载诊断密集，C# 侧诊断生成路径慢（r17/r18 两代读数一致） |
| tiny-files-noemit | x1.30，且相对自身基准 −8.7% | DATAS 关闭后该形态的既有代价（r18） |

**一句话**：r23 把 C# 对 Go 的重负载差距压到平均 1.43 倍，最好项（declarations x1.20、medium x1.25）已接近同一量级；剩余差距的主体是单检查器串行路径（x2.06）与 55 ms 启动地板。分配侧 5.1 倍差距的大头是合法工作本体（节点/符号/类型图两边尺寸相当，C# 无逃逸分析 + 对象头），已接近该 substrate 的地板。

## 6. 口径与批次有效性

### 6.1 采纳的批次

| 批次 | 用途 | 控制项 p95rel | 控制项 medianRatio（CI） | 行级 spread 最大值 | 处置 |
| --- | --- | ---: | --- | ---: | --- |
| AB109 | r23 vs Go 默认 | 40.5% | 1.010（[0.986, 1.050]） | 1.35 | 采纳 |
| AB113 | r23 vs Go@400 | 6.7% | 0.985（[0.971, 1.016]） | 1.64 | 采纳 |
| AB114 | r23 vs C# 基准 | 30.1% | 1.011（[0.995, 1.046]） | 1.81 | 采纳 |

AB109 的 p95rel 超过历史判废线（r11 的 35.2%），但判废实质依据是槽位偏置而非离散度：该批控制项 `medianRatio` 1.010、CI 紧且含 1.0，23 行的行级 spread（p95÷min）全部 ≤1.35，两个槽位无系统偏置。高 p95rel 来自 `--version` 控制项在本机同时运行的其他进程下的离散，与 r18 表采纳 AB97（45.0%）的理由相同。

### 6.2 弃用的批次（记录在案）

| 批次 | 用途 | 失败形态 | 处置 |
| --- | --- | --- | --- |
| AB111 | r23 vs C# 基准（第一轮） | 4 行基准槽 + 3 行 r23 槽 spread > 3（最大 20.1）；`host-paths` 基准槽 min 106 / median 1432 ms | 整批弃用，重跑为 AB114 |
| AB112 | r23 vs Go 默认（第一轮） | 18/23 行 r23 槽 spread 3.7~23.1（`version` 18.9、`project-references-implementation` 23.1）；同一批 Go 槽稳定在 82~92 ms，r23 槽 134~1753 ms 随机跳 | 整批弃用，重跑为 AB109 |
| AB110 | r23 vs Go@400（第一轮） | 每行 spread ≤1.47，控制项 15.3%，本身有效 | 保留但未被采纳（与 AB113 同用途，取控制项更优者） |

AB111/AB112 的失败均无外部 CPU 解释（AB112 的外部 CPU 消耗低于被采纳的 AB109，RSS 与 AB109 相同，机器 20.9 GiB 空闲），形态是同一二进制在个别批次内出现随机倍率跳变；两批的 Go 槽与另一批的 r23 槽均稳定，因此判为批次级扰动而非代码或配置属性。**这也说明本机当前不具备把 1~2% 的墙钟效应测准的条件**（r21~r23 三轮合计 −4.6% 分配在墙钟上只剩批间噪声，与此一致）。

## 7. 表内数字的校验

计时表 23 行的四个中位数、改善 CI 与两个 Go 比值，由脚本 `built/r23-threeway-table.mjs` 直接读取三个 summary.json 生成，非手工转录；分配表三组数字为同一会话内直接运行产品二进制加 `--extendedDiagnostics` 得到（naot-svr 两次、r23 三次）。
