## 1. 结论

方案 B（跳过 union 排序、共享排序基准）**不通过判定**。

proto.ts 的排序内比较共 577,500 次，去重后 528,779 对，重复率 **8.4%**。按比较对记忆化最多省 226 ms 的 8.4%（约 19 ms），而每次比较要额外付一次字典查询与哈希，782,138 次调用的查询开销大概率超过这 19 ms。这 8.4% 主要来自排序算法自身的重复比较，不是跨 union 归约的复用。

我上一轮给出的 8~12% 端到端预期是错的。错在把「输入集合不同」误推成「比较工作可复用」。实测显示输入不同意味着比较对几乎完全不同：约 1,000 次大 union 归约产生近 53 万个互不相同的比较对。这正是「大量不同的必要工作」的量化形态。

## 2. 测量方法

临时探针 `TSHARP_SORT_PROBE`（量后 `git restore` 回退），在 `TypeOrder.Compare` 出口记录：

1. 比较对 `(TypeOrder 实例, left.Id, right.Id)` 与返回结果；
2. 是否落在 `AddUnionTypes` 的 `Sort` 内（`[ThreadStatic] InUnionSort` 标记）；
3. 首次出现的比较对计入 distinct，重复出现且结果不同计入 unstable。

夹具为真实工程（291 文件图），`--noEmit`，产品配置，运行前删除两个 tsbuildinfo。

### 2.1 一处探针缺陷及其修正

首版用全局静态 `(left.Id, right.Id)` 作键，读到 `unstable=4016`。原因是不同 checker 有独立的 `Type.Id` 空间，跨 checker 的同号 id 是不同对象，键碰撞被误判为结果不稳定。

修正为按 `TypeOrder` 实例分域后，`unstable=0`。这同时证明比较器是纯函数：同一实例内同对必得同结果。

## 4. 为什么共享基准不成立

方案 B 的原假设是：176 个分支各构造一次约 176 成员的 union，输入集合虽不同，排序基准相同，可以共享。

实测反驳：

- 若基准真能共享，各分支的比较对应有大量重合，distinct 应显著小于 calls。
- 实际 distinct / calls = 0.91，即 91% 的比较对只出现一次。
- 每个分支的 union 成员来自不同的实例化结果，`Type.Id` 各不相同，比较器按 id 与结构排序时看到的是不同对象。

所以「同一基集合的子集」这个前提不成立。176 个分支各自产生独立的类型对象，union 归约处理的是 176 份不同数据。

## 5. 方案 A 的估计修正

r42 给方案 A（降 `TypeOrder.Compare` 常数）估了 15~30 ms。既然比较对重复率仅 8.4%，说明每次比较都在处理新数据，常数压缩空间仍在（`Interlocked` 池化、`Part` 装箱、三处 push 合并），但那 15~30 ms 是常数项的 10~20%，不是重复劳动的消除。

结论不变：方案 A 零风险但低于 1.1% 噪声下限，不该单独占一轮。可作为后续任何触碰 union 路径的轮次的顺带项。

## 6. 本轮关闭清单更新

| 项 | 关闭依据 |
| --- | --- |
| infer memo | 本仓推断走查平均 2.7~4.1 步，无 tsrs 的巨型走查形状 |
| union front cache | 残余重复调用均值 0.85 µs，命中开销吃平收益 |
| flow walk memo | 跨 walk 重访 23.3%，键需扩四元组 |
| 跨 checker 类型层共享 | tsrs 四种形态被 2% 预算挡死，与 L1 仲裁独立同结论 |
| 按比较对缓存（方案 B） | 重复率 8.4%，低于查询成本 |
| 分发批量化 | 各分支比较对几乎完全不同，无共享基准 |

六项结论指向同一件事：本仓检查相位的成本是必要工作的常数问题，不是重复劳动，也不是算法浪费。这决定了后续性能工作应该找「能不能少做」，而缓存类方案（记住做过）方向错误。

## 7. 剩余空间

检查相位已接近单文件下限：`partition#1` 独占 checkPool 的 99.8%，其中 proto.ts 占 63%。在检查相位内继续找收益的期望值很低。

唯一还有量级的是 L4（默认 lib 预绑定，Program 固定成本 0.300 s，占 Total 1.235 s 的 24%）。它与已关闭的共享类型层不同：只共享默认 lib 的绑定产物，规模小两个数量级，属于 tsrs 那个被否决设计的子集。它是架构级改动，需要先做所有权设计评估。
