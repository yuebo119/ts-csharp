## 2. 落地内容

### 2.1 `TypePredicates.Maybe` 的遍历不再分配工作栈

`Maybe` 判断一个类型（或联合/交叉的任一成员）是否带某组标志位，32 处调用点覆盖实例化、加宽、字面量推断、流分析、多余属性等热点路径。原实现每次都 `new Stack<Type>()` 再把类型压进去走一遍，**单类型这一最常见输入也要付一次 `Stack` 加后备数组的分配**。

改为三段，语义逐条等价：

| 输入 | 现实现 | 与原实现的等价性 |
| --- | --- | --- |
| 单类型 | `cancellation.ThrowIfCancellationRequested()` 后直接测标志位 | 原实现压栈、弹栈、测的是同一个 `type.Flags`，结果相同 |
| 联合/交叉（成员已被扁平化） | 直接顺序扫描 `Types` | 原实现把成员压栈后逐个弹出测标志位，是同一组标志位测试；结果只取决于"是否存在"，与顺序无关 |
| 成员自身仍是联合/交叉（防御分支） | 落到 `Nested`，保留原工作栈 | 与 r12 及更早行为逐字相同 |

扁平化不是假设而是构造事实：`TypeAlgebra.AddUnionTypes` 在构造联合时把嵌套联合的成员并成一个列表，因此 `UnionType.Types` 的成员不会是联合。`Nested` 分支保留，是为了让"成员仍是复合类型"这一情形继续按原样工作，不依赖上述构造事实。

### 2.2 归因纠正：r09/r10 剩余清单里的"实参位置重复查询 17.9 MB"不成立

r09/r10 的剩余清单写着「实参位置的上下文类型重复查询 17.9 MB，需按节点+flags 记忆化」。本轮先量化这条再动手，结论是**标签与数字来自不同位置，该条不成立**：

| 检查 | 实测 |
| --- | --- |
| 巨文件是否有实参位置查询 | **0 次**。该夹具只有 `export const valueN: {...} = {...}` 形态，没有调用表达式 |
| 真实工程的实参位置查询 | 798 次，其中重复 183 次（23%） |
| `ctxArgument` 帧（签名解析 + 形参类型查询） | 在巨文件为 0；在真实工程未进入探针前 24 名，即 **< 0.73 MB** |
| 17.9 MB 的真实出处 | 巨文件的 `mutableContextual` 帧（本轮重测 13.4 MB）。那是**每个属性一次**的加宽阶段上下文查询，不是重复查询 |

重复查询本身已在 r08 被门控消除：`TypeParameterQueryPossible` 排除了非实参位置，剩余的双查询只发生在实参位置的字面量上，而那个量级低于 1 MB。**结论：不需要按节点+flags 做记忆化，那条改动会引入推断期失效风险却换不到可测量的收益。**

### 2.3 顺带纠正的一条假设：上下文链的开销不在异步框架上

r12 把上下文查询链的剩余开销归给"异步调用链"，本轮用内层探针拆开 `ApparentAsync` 后否定了这一点（巨文件，探针帧为并行检查器求和值，只作相对比较）：

| 内层帧 | 巨文件 | 真实工程 |
| --- | ---: | ---: |
| `ctxApparentInst`（`InstantiateAsync`） | 5.77 MB | 4.49 MB |
| `ctxApparentMap`（`MapAsync` + 闭包） | 3.67 MB | 1.38 MB |
| `maybe`（全量调用点） | **8.65 MB** | **10.95 MB** |

`InstantiateAsync` 在巨文件上 32,768 次调用全部走提前返回，每次 176 B，而它的提前返回分支只做一件事：调 `Maybe(type, Instantiable)`。也就是说 `ctxApparentInst` 的 5.77 MB **全部是 `Maybe` 的工作栈**，不是异步状态机。修复后 `maybe` 帧消失，`ctxApparent` 帧从 9.96 MB 降到 4.19 MB，`objectLiteral` 帧同步降 7.2 MB（`Maybe` 也在对象字面量检查内部被调用）。

## 5. 测量纪律记录：一批被判废，四批被采纳

本轮共跑五个配对批次。其中 `bench/AB77-r13-vs-r12`（23 负载 × 21 组交替配对）的同可执行文件控制项：

| 控制指标 | 值 |
| --- | --- |
| `p95RelativePairDifference` | **1.662**（166%） |
| 同可执行文件 `medianRatio` | 0.525（同一份二进制的 before 槽比 after 槽慢一倍） |
| 95% bootstrap | [0.234, 1.008] |

该批次记录的机器活动显示，运行期间存在与本任务无关的持续 CPU 消费者：`PalDDD.Benchmarks` 835 CPU 秒、宿主自身进程 914 CPU 秒，另有 `VBCSCompiler`、输入法、显卡驱动等。同可执行文件在两槽之间差一倍，说明差异来自槽位所在的时间段，而非被测代码。

处置：该批次只取**逐字节产物比对**结果（与负载无关，见 §3），墙钟与峰值内存列全部弃用。这是本项目第二次因控制项整批判废（前一次是 r11 的噪声 35.2%）；另有两次同类教训不属于批次判废：r07 的轻负载批内偏置，r12 的 CoreCLR 结论不迁移到 AOT。
