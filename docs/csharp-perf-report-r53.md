## 1. 结论

**emit 相位此前从未被归因，本轮补上：它是 Total 的 19%（full 模式约 0.20~0.22s / 1.09~1.13s），且其结构是「每属主一个串行段」。**

结构决定上限：每个文件只能由**属主 checker** 发射（`CheckerPool.AcquireAsync` 按静态分区映射租借），所以 emit 墙钟 = max(属主负载) + 阻塞尾巴。实测 8 个属主的 emit 负载为 **68~179ms**（均值约 112ms），最重属主 176.9~178.6ms 就是墙钟下界。

两条路径的处置：

| 路径 | 机制 | 实测 | 处置 |
| --- | --- | --- | --- |
| 全局队列按成本降序（LPT） | 大文件先启动，压低 makespan | 相位墙钟 0.308/0.309s（同构建对照臂 0.202/0.208s）、阻塞工时 935/1024ms（对照 365/395ms） | **否决**：最大文件集中落在少数属主，全部先启动反而让其余工位堵在这些属主后面 |
| 按属主派发（每属主一个 task） | 工位不再因等待属主而空转 | 阻塞工时 **365~395ms → 0.0ms**，相位墙钟 0.208 → **0.182/0.193s**，端到端 60 对中位比 1.0257 CI [0.993, 1.087] | **搁置**：机制成立、门禁全过，但端到端落在本机噪声地板内（同代码对照批自身读出 2.4% 伪差），按判据不发布 |

附带否定两条既有待勘/估值：

1. **L4（lib 预解析 + 预绑定）可关闭**。空项目实测（1 个源文件 + 完整 es2020 lib 链 52 文件）：Program 仅 **0.037s**，其中 Parse summed 0.025s、Bind summed 0.024s——整条 lib 链的 Program 成本上限就是这 37ms（≈Total 3.4%），且预绑定还要付反序列化成本。真实工程 full 模式 `--noLib` 差分只有 **0~13ms**（Program 0.174~0.188 vs 0.175~0.183，两组读数重叠，单独不作为证据），方向与上限一致。r37/r39 记录的「lib 层占 Program ~0.15s」是旧口径，本轮复核不成立。
2. **emit 并行度旋钮 8 工位已最优**：现成旋钮 `TSHARP_EMIT_CONCURRENCY` 实测 serial 1.939~2.250s、8 工位 1.058~1.121s、16 工位 1.096~1.141s（16 无增益，与检查器数「8 见底」同族）。

## 2. 为什么 emit 此前没有归因面

`--extendedDiagnostics` 的相位作用域覆盖检查侧（`phase:partition*`/`checkPool`/`constructEach`/`globalMerge`…），**emit 侧一个都没有**。可读的 `Emit time (summed) 0.925~0.965s` 是逐文件墙钟求和，与真实墙钟差 4~5 倍，不能当相位预算用（本轮探针实测 emit 相位墙钟只有 0.20~0.22s）。

本轮用临时 `TSHARP_EMIT_PROBE`（每文件记录：调度偏移、租借等待、主体耗时、写盘耗时，并按属主归集；量后回退）把这段拆开。

## 4. 机制：属主亲和 × 共享队列

`CheckerPool` 把文件静态分配给 8 个 checker（`CheckerPartitions.ForProgram`，参考实现校准的 FENNEL 权重），`AcquireAsync(file)` 按该映射租借**属主** checker 的闸门。emit 循环（`IncrementalProgram.Emit.cs`）原形态是 `Parallel.ForAsync(0, work.Count)` 取序号即自增的共享队列：**工位取到文件后若属主忙，只能阻塞**。

同一会话内两臂对照（真实工程 full，`TSHARP_EMIT_PROBE`）：

| 属主 | 文件数 | queue 臂 work / wait | owner 臂 work / wait |
| ---: | ---: | --- | --- |
| 0 | 21 | 111.8 / 39.7 ms | 105.1 / **0.0** ms |
| 1 | 11 | 178.6 / 15.4 ms | 176.9 / **0.0** ms |
| 2 | 9 | 126.9 / 52.7 ms | 117.9 / **0.0** ms |
| 3 | 21 | 92.3 / 110.0 ms | 88.2 / **0.0** ms |
| 4 | 25 | 92.1 / 95.2 ms | 92.6 / **0.0** ms |
| 5 | 16 | 93.4 / 50.7 ms | 93.5 / **0.0** ms |
| 6 | 3 | 159.1 / 0.0 ms | 155.8 / **0.0** ms |
| 7 | 7 | 71.5 / 0.9 ms | 68.1 / **0.0** ms |
| 合计 | 113 | 925.8 / **364.5** ms | 898.2 / **0.0** ms |
| 相位墙钟 | | **0.208s** | **0.182s** |

三条读数：

1. **墙钟 = 最重属主负载 + 尾巴**。owner 臂 182ms 对最重属主 176.9ms（差 5ms）；queue 臂 208ms 对最重属主 178.6ms（差 29ms，即阻塞尾巴）。
2. **阻塞工时可观**：queue 臂 364.5ms（另一轮 378.9/395.3ms）。8 工位 × 0.208s = 1664ms 可工时，阻塞占 ~22%。
3. **属主负载本身不均**（68~179ms，max/mean = 1.6），这是参考实现权重模型在 emit 侧的固有结果（`proto.ts` 权重 510 但 check 253ms 的反向失明属 r39/r52 同一族）。

## 5. 被否决的路径：全局队列按成本降序（LPT）

先验思路是经典 makespan 修法：按文件成本降序启动，把墙钟压到 `max(最大文件, 总工作量/工位)`。权重代理已验证可用（静态权重与实测 emit 成本近似线性，约 3.1 µs/单位，排序在 12 个最大文件上几乎一致；`sync/api.ts` w=41057 → 139ms、`factory.generated.ts` w=41761 → 128ms）。

同构建三臂实测（真实工程 full，`TSHARP_EMIT_ORDER` = source / lpt / owner）：

| 臂 | 相位墙钟 | sumWork | sumWait | maxWork |
| --- | --- | --- | --- | --- |
| source（程序序，共享队列） | 0.202 / 0.280s | 873.6 / 1174.8 ms | 378.9 / 705.8 ms | 131.1 / 129.0 ms |
| **lpt（成本降序，共享队列）** | **0.308 / 0.309s** | 1481.5 / 1401.8 ms | **935.1 / 1023.9 ms** | 235.9 / 229.2 ms |
| owner（按属主派发） | 0.185 / 0.264s | 1004.8 / 1670.0 ms | **0.0 / 0.0 ms** | 146.2 / 225.0 ms |

LPT 在两轮都更差，且机理与读数同向：最大的 8 个文件里若有多个共享同一属主，把全体大文件一起前置，就等于让 7 个工位同时堵在同一个属主闸门上——阻塞工时从 ~380ms 涨到 ~940~1024ms。**「共享队列 + 成本排序」不成立，因约束不是工位数而是属主闸门。**

另有一处负结果：在 owner 臂内部再按成本降序（属主内 LPT）会把 sumWork 抬高约 15%（1401~1481ms vs 898~1005ms），因为它反转了该属主 checker 在检查期已经预热的文件顺序。属主内应保持 own order。

## 6. 被搁置的路径：按属主派发

实现（补丁留档 `tsbench/r38/r53-emit-owner.patch`，71 行）：`work` 按属主归集成 8 个列表，每个属主一个 `Task.Run`，各自持有自己的闸门、按 own order 顺序发射自己的文件；结果仍按原索引写回 `results[index]`，发布顺序不变。`TSHARP_EMIT_ORDER=queue` 保留旧共享队列供同二进制 A/B。

门禁七项全过（构建产物 `built/r53-final`，对照 `built/r51-final`）：

| --- | --- |

| 6 夹具逐字节产物 | `perf-verify`：201 产物（退出码 + stdout 哈希 + 发射文件哈希）**pre == post 全等** |
| 诊断流 | `errdense` 5001 行 stdout 逐字节相同 |
| traceResolution | `dtsheavy` 1208 行逐字节相同（措辞依赖探测布尔值，任一差异即翻） |

增量轮是本改动最需要盯的场景：tsbuildinfo 记录「最后一个变更声明」（`LatestChangedDtsFile`），而发射顺序被本改动改变。实测该字段两臂一致、空转轮稳定。

| 批次 | 模式 | 对 | owner 中位 | 对照 中位 | 比值（对照/owner） | 95% CI | CPU 中位 |
| --- | --- | ---: | ---: | ---: | ---: | --- | --- |
| 4 臂构建 | full | 40 | 933.3 ms | 958.0 ms | 1.0265 | [0.978, 1.049] | 5391 vs 5203 |

判读：两批 full 中位都在 2.6% 附近且方向一致，与相位读数（0.208→0.182 = 26ms，占总 2.5%）吻合，机制自洽；**但两种模式的 CI 都含 1.0**，而 noemit 对照批两臂代码完全相同、仍读出 2.4% 的差异（方向还相反）——即本机在 20~60 对尺度上的伪差地板就是 ~2.4%，2.6% 落在其中，不可判。CPU 侧同理（对照批自身也差 3.2%）。

## 7. 结构性上限：emit 轴整体 ≤3%

即使（a）阻塞完全消除、（b）8 个属主负载完全均衡，emit 相位墙钟下限也是 `max(最大单文件 ~139ms, sumWork/8 ≈ 112~121ms) ≈ 139ms`——相对现状 0.208s 只剩 **~60ms 空间（总 5.5%）**；而（b）需要改参考校准的 `CheckerPartitions` 权重（r39/r52 已把「静态权重可预测」证伪，且改分区=与参考实现分叉，需用户裁决），实际可达的只有（a）的 ~26ms。

再往下只能削**每文件工作本身**（打印常数、声明变换），属 r35 W3「字面量形状结构体化」家族（真实工程预期 ≤3%，同族 sub-noise）。**结论：emit 相位在本机分辨率尺度上已无 ≥5% 的可兑现杠杆**——这与 r43「检查相位是必要工作的常数问题」、r51「解析已压到信息下限」构成同族结论。

## 8. 复现口径与已知边界

- 探针 `TSHARP_EMIT_PROBE`（每文件：调度偏移、租借等待、主体耗时、写盘耗时，按属主归集），`TSHARP_EMIT_ORDER`（source / lpt / queue / owner 四臂），全部量后回退；`phase:emitCore` 作用域亦随探针移除（避免改动 `--extendedDiagnostics` 的可观测输出）。
- 探针首版有两处缺陷已修：`Write()` 先于 `File()` 建条目把 `Start` 污染为 0（off 读数作废，改用 `long.MaxValue` 兜底）；`Owner` 在更新分支里写成 `value.Owner` 而非入参，导致属主恒为 −1。
- 本报告相位数字取自 `--extendedDiagnostics` 运行（含强制全量 GC 与统计遍历），绝对值比门禁批次偏高；**端到端判据一律用不带该旗标的配对批次**。
- 每轮运行前删夹具根 `tsconfig.tsbuildinfo` / `tsconfig.enums.tsbuildinfo`（r44/r45 污染陷阱）；批次间绝对水平漂移达 +19%（full 中位 933→1108ms），跨批只读比值。
- 本轮一次构建失败的教训：`dotnet publish … | grep -E "error|warning" | head` 的管道退出码来自 `head`，把编译失败读成了 exit 0；编译类命令必须直接取退出码。
- `Task.Run(async () => {…}, cancellation)` 的重载歧义（async lambda 同时可转 `Func<Task>` 与 `Action`）在本轮触发 CS1026，改用显式局部 async 函数。

## 9. 剩余空间

- 检查相位（0.52s / 47%）：最大块仍是关系引擎族（r52 §8），受 r27 表 3 约束；EventPipe 对本机 AOT 仍挂接不通。
- **emit 相位（0.20s / 19%）：本轮关闭**，无 ≥5% 杠杆（§7）。
- Program（0.17s / 17%）：r50/r51 已连续两轮压过；余量是串行发布/应用循环。
- 启动地板 121~141ms：r30 已判为 .NET AOT 与 Go 二进制的 substrate 差，不可修。
- 待勘区仅剩的可动项都低于本机噪声地板（emit 属主派发 2.5%、W3 字面量结构体化 ≤3%、L4 已关闭）——**战役的下一步需要更高分辨率测量环境，或转向「减工作量」的架构级改动（如声明发射复用/裁剪）而非调度与缓存**。
