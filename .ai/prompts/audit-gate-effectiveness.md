# 专项：门禁有效性审计（只读，变异测试）

派生自 `master.md`。先读它的 §0 与 §1，本文件只写任务加料。

## 为什么做这个

18 万行编译器，门禁只有两样：6 个逐字节夹具、94 个 safety 旗标（跑 94 项）。没有覆盖率数据，没有单元测试框架，没有变异测试，没有 fuzz 语料。r44 已经给过一个实例：首版 union 逆序插入实现有真实的正确性缺陷（取错侧时逆序出现在别处，邻域检查漏判），而逐字节门禁全过。这说明「门禁绿」与「实现对」之间有一条没被测量的缝。

## 目标

量化现有门禁能拦住多少真实缺陷，找出结构性盲区，给出补测优先级。

## 方法

### 1. 覆盖率基线

用 `dotnet-coverage` 或 coverlet 对 Compatibility 台架跑一遍全覆盖，产出按目录的行覆盖率与分支覆盖率。工具不可用就明说不可用并跳过这一步，不要用估算代替。

按目录聚合：Checking / Binding / Syntax / Emission / Resolution / Incremental / LanguageServices / LanguageServer / Api / Text / Storage / Projects。

### 2. 手工变异矩阵

选 10 个高风险站点，每个注入一个语义变异，跑全套门禁，记录结果。高风险站点建议：

1. 关系引擎的比较或缓存判定（`Checking` 下关系相关文件）
2. union 归并的段边界（r44 / r45 / r48 的落点）
3. 增量失效判定（声明签名比较、buildinfo 读取）
4. 诊断排序或去重
5. 打印器位置计算（行号、列号、source map 映射）
6. AST 编解码器的字段顺序或长度编码
7. 路径解析的候选扩展名顺序
8. 编码转换（UTF-8 / WTF-8 转换分支）
9. 约束求解的求解顺序
10. 控制流图的边构造

变异形态：边界 ±1、条件取反、去掉一次去重、交换两个顺序、把守卫阈值改大。

### 3. 结果分类

每个变异落入三类之一：

- 变红：门禁拦住了。记录是哪个夹具或哪个 safety 旗标拦住的。
- 没红：门禁盲区。这是本次审计的主要产出。
- 编译失败：变异本身无效，换一个。

对「没红」的每一条，判断成因：夹具覆盖不到该行为，还是断言本身不检查该行为，还是该路径根本没有测试。

### 4. 断言强度抽查

读 10 个 safety 旗标的实现，判断它是「跑通即通过」还是「钉死具体契约」。后者才是真门禁。抽查建议偏向被 ledger 引用过的旗标（如 `checker-program-safety`、`module-program-specifiers-safety`、`checker-relation-context`）。

## 输出

1. 覆盖率表（按目录，行 / 分支）
2. 变异矩阵（站点 × 变异 × 门禁是否变红 × 拦住它的载体）
3. 盲区清单，每条带「补测方式」与「该代码的真实风险」
4. 断言强度分级：强契约 / 弱存在性 / 形式化
5. 补测优先级排序，判据是「变异存活 × 该代码在生产中的暴露面」

## 边界

只读。所有变异必须回退，收尾时 `git status` 干净。不许把「通过率」当门禁有效性的证据，通过的测试可能什么都没断言。
