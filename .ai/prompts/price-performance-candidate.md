## 禁止提案清单

以下每一条都在 ledger 里有否决数据，重提就是浪费整轮：

- 缓存族：infer memo、union front cache、flow walk memo、按比较对记忆化
- 跨 checker 共享只读类型层或符号层
- arena、紧凑类型对象、结构体化类型节点
- checker 数量调整（4 / 8 / 16 / 20 / 32 全测过）
- parse / resolve 并发度调整
- 调度重排：L3-a 动态认领、LPT 全局降序、静态权重再标定
- checkpoint 数量、GC 堆数、GC 延迟模式、no-GC region
- lib 预解析 / 预绑定
- 启动路径优化（`--version` 的差距是运行时初始化基座，本仓不可修）
- 扫描器内部微优化（已定界在噪声以下）

## 允许的开口

1. 新负载形态。CLI 战役的语料全是干净工程，以下形态没有被测量过：
   - 错误密集型（`errdense` 夹具已有：200 文件 × 25 错，5000 诊断）
   - 顶层 await（真实工程 113 个文件里为 0）
   - sourceMap 编译
   - LSP 长驻（补全、悬停、诊断的请求响应延迟）
   - watch 模式的单次触发延迟
   - API 传输（MessagePack 同步 / JSON-RPC 异步）
   - 增量编辑轮（ledger 有 editbig 数据，但只测了 emit 分配）
2. 长驻与增量场景的延迟。ledger 明确写过「watch/LSP 长驻形态深审计超出 CLI 战役范围，记录而非永久否决」。每次编辑到诊断出现的延迟是用户真实感知的指标，从未被端到端测量。
3. 测量环境。本机同代码伪差地板 2.4%，控制组 CI 常宽 ±5~10%。任何能提高判据分辨率的投入（更安静的机器、更多核、更好的控制组设计）比 3% 的代码优化更值钱。

## 方法：探针门槛制

先写只读探针证明目标存在，过门槛才谈原型。

门槛分两档（沿用 r40 分档）：

- 独立档：目标占 checkPool 或对应相位 ≥ 5%，可独立发布
- 叠加档：≥ 2%，只随累计变更集发布

每条候选必须给出：

1. 目标：哪个相位、哪个函数、哪类调用
2. 探针设计：计数什么、闸门怎么加、量完怎么回退
3. 门槛与预期上限：上限 = 该面占比 × 可消除比例 × 上游稀释系数
4. 风险：是否触碰关系调用链、是否改输出顺序、是否影响 AOT 布局

预期上限算清楚再动手。历史教训：r45 理论上限 4% 落在 ±5~10% 分辨率内，端到端测不出；r48 上限 13% 才测得出。上限低于 5% 的候选，不要花整轮去测。
