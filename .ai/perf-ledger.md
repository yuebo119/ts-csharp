本轮证伪（数据留档，勿重提案）：

| 项 | 证伪数据 |
| --- | --- |
| 「多 checker 分配 ×3.3」 | 假象：`Alloc X (summed)` 在并行相位重叠重复计数。进程总量口径：medium 8 checker 315.5 MB vs 1 checker 284.0 MB（+11%），tiny512 245.5 vs 231.7 MB（+6%）。真实代价是 CPU（summed check 2.2 s→3.6~4.0 s）与类型对象（+31%）；墙钟 8 checker 反而 −19%（medium）/持平（tiny512） |
| 自适应下调 checker 数（小项目 1~4） | 反向：small3（3 文件）默认 8 checker 2.77 s vs `--checkers 1` 3.07 s（比值 1.11）。每 checker 的 lib 推导可并行摊薄，下调反而更慢 |
| checker 数上调（>8） | tiny512 c8 2972 ms → c32 2789 ms（−6.2%）但 medium c8 2830 → c32 2985 ms（+5.5%）；文件数重负载可作旋钮选项，默认不动 |
| checker 数下调（扫描读数 → 配对推翻） | 未配对扫描（3 次中位）曾显示 c4/c2 常胜 c8（medium 2658 vs 2897、dtsheavy 2334 vs 2835）；按仓库配对协议交替 5 对复测：medium c8 比 c4 快 4.7%（比值 0.9526），dtsheavy c2/c8 比值 1.0401、tiny512 1.0017、huge 1.0044，均落在噪声带内。结论：默认 8 检查器成立，不调；扫描式（非配对）读数的漂移量再次被实测标定为 ~±10% |
| `S()`/`Scoped()` 元数特化省分配 | 前提不成立：`parts.ToArray()` 即 Parts 容器的唯一必要分配，特化后仍是同一份数组 |

| 配方（recipe）token 切点缓存 | 收益面窄：容器免分配路径已覆盖多数节点，recipe 扫描不分配；缓存键须处理切片文本，风险大于收益 |

判定：重复推导真实存在（CPU +27~108%、类型 +4~31%），但进程分配代价温和（+2~11%），且墙钟在 c8 与 c2/c4 之间仅 ±4%（配对复测，见上表证伪行）。结论：P2-11 的价值主张是"墙钟上限"而非分配，开工前仍需真实工程夹具的重复推导占比（本检出无 `packages/typescript`）与 `RequireOwned` 所有权解耦设计，维持不立项。附带定标：本机 `Program time` 固定成本 ~0.29 s，其中默认 lib 层（lib.es2017.full 链，30 文件）占 ~0.15 s；模块解析密度不影响该值（64 文件 × 20 import 与 × 2 import 的 Program time 相同）。

skipLibCheck 口径校准（2026-10-15 补，比较本报告数字前须对齐）：medium 未开 skipLibCheck 时 check 3.86 s summed / 670 MB、总墙钟 2.38 s；开启后 check 1.86 s / 270 MB、总墙钟 1.13 s（lib 与 .d.ts 检查占 check ~52%、总墙钟 ~53%）。dtsheavy 开启后 check 0.13 s（全部 .d.ts 被跳过）。

**r53 emit 相位归因普查与属主派发搁置（2026-10-22，docs/csharp-perf-report-r53.md，产品代码零改动）**：用户令「结合 C# 新特性优化」（与 r44 同一条指令）。①**emit 相位此前从未被归因**（无 `phase:` 作用域，`Emit time (summed)` 是逐文件墙钟求和，与真实墙钟差 4~5 倍）：临时 `TSHARP_EMIT_PROBE` 实测其墙钟 **0.202~0.220s（Total 19%）**，结构是「每属主一个串行段」——文件只能由属主 checker 发射，故相位墙钟 = max(属主负载) + 尾巴；8 属主 emit 负载 **68~179ms**（max/mean 1.6），最重属主 176.9ms 即墙钟下界。②**共享队列的代价**：工位取到文件而属主忙时空转，阻塞工时 365~395ms（占 8 工位可工时 22%），尾巴 29ms（208 vs 179）。③**按属主派发**（每属主一 task、保持 own order）：阻塞 → 0.0ms、相位墙钟 0.208 → 0.182/0.193s，门禁七项全过（6 夹具 201 产物 / errdense 5001 行 / traceResolution 1208 行 / singleThreaded / safety 90/93 ⊆ 基线 / 自建增量多文件轮 129 产物 × 3 轮含 tsbuildinfo 全等）；但端到端两批（40 对 1.0265 CI [0.978,1.049]、60 对 1.0257 CI [0.993,1.087]）CI 均含 1.0，且**同代码 noemit 对照批自身读出 2.4% 伪差**（0.9764 CI [0.942,1.016]）→ 2.5% 落在本机伪差地板内，按 r40 发布判据（CI 不含 1.0，否则全额回退）与 r52 先例（更大的相位收益同样否决）**搁置**（**r54 用相位级配对证据复审后发布，见下条**）。补丁 `tsbench/r38/r53-emit-owner.patch`（71 行，含 `CheckerPool.OwnerOf` 与 `TSHARP_EMIT_ORDER` 旋钮），复活前置：更高分辨率环境 40 对 CI 排除 1.0。④**结构性定界**：即使零阻塞 + 属主负载完全均衡，emit 相位下限 ≈ max(最大单文件 ~139ms, sumWork/8 ≈ 120ms) ≈ 139ms，即**调度轴整体 ≤3%**（≈Total 5.5% 空间）；均衡化需改参考校准的 FENNEL 权重（r39/r52 已证伪「静态权重可预测」，且属与参考分叉的用户裁决面）；更深只能削每文件工作量（r35 W3 字面量形状结构体化家族，真实工程 ≤3%）。**附加两条否定**：emit 并行度 8 工位已最优（旋钮实测 serial 1.939~2.250s / 8 工位 1.058~1.121s / 16 工位 1.096~1.141s）；**L4 关闭**（见表 2）。emit 轴关闭。

**r54 emit 属主派发发布 + 相位墙钟可见化（2026-10-22，docs/csharp-perf-report-r54.md，产品代码 2 文件 44 行）**：用户令「结合 C# 新特性和 tsrs 经验优化当前项目」，即 r53 的复审轮。①**补上了 r53 缺的那层证据**：新增 `phase:emitTotal` 永久相位作用域（`Measure` 无捕获时 no-op，普通运行零成本），同二进制两臂交替 **30 对** 实测 owner 中位 **0.2120s** 对 queue **0.2380s**，比值 **1.1226 CI [1.022, 1.407]，区间排除 1.0**——相位墙钟逐次噪声远小于整进程墙钟，这是 r53 搁置时唯一缺的东西（当时只有两次非配对读数）。②**端到端如实分层**：三批 full（r53-3arm 40 对 1.0265 [0.978,1.049]、r53-final 60 对 1.0257 [0.993,1.087]、r54-final 30 对 1.0371 [0.973,1.110]）中位方向一致（2.6%~3.7%）但 CI 全含 1.0；同代码 noemit 对照批自身 2.4% 伪差（0.9764 [0.942,1.016]）标定地板；CPU 方向在三批间翻转（+2.1%/+2.4%/−1.9%）故不可判。**只宣告相位 −12.3%，不宣告端到端收益。**③**门禁六项全过**：构建 0/0、6 夹具 201 产物逐字节、errdense 5001 行、dtsheavy traceResolution 1208 行、medium --singleThreaded、safety 90/93 ⊆ 基线、editbig 增量三轮 129 产物含 tsbuildinfo 全等。④**结构性推论（新）**：check 与 emit 的**最重属主是同一个**（partition#1 含 `proto.ts`，检查 0.401s；其 emit 负载也最大 176.9ms），故 max(check)+max(emit) = max(check+emit) = 0.578s 逐项相等——**流水线化 check→emit 在本负载上恒等**，这解释了 r39-L3-a「checkPool −17% 端到端 1.006」是结构必然而非 emit 尾部偶然。任何只改「相位如何排列」的方案都不改变关键路径。⑤**附带否定**：启动地板是环境性的（`--version` C# 90ms / Go 80ms，而原生 `cmd.exe /c echo` 61ms、`where.exe` 131ms），r30 的「x1.87 基座差」在 `--version` 口径下不成立（约 1.1），该 11%~13% 墙钟占比对所有二进制同等，非代码目标；打印侧量级：full 的 `Print summed 0.694~0.749s` 对 `Transform summed 0.205~0.210s`，输出 7.39 MB（6.74 JS + 0.65 d.ts），成本以 JS 打印为主。⑥**消融陷阱**：`-p tsconfig.json --declaration false` 触发 TS6304（composite 不得关声明）后**检查相位被整体跳过（Check 0.000s）却仍发射**，该形态不可用于 print 分解，本轮弃用；报错仍发射与参考是否一致未查证，留后续。

**r55 Program 相位归因（2026-10-22，docs/csharp-perf-report-r55.md，两条利用路径否决，产品代码零改动）**：用户令「继续按最优方案优化」，即 r54 之后唯一未到行级的大块（Program 0.17s / Total 17%）。①**串行发布循环不是余量**：roots 趟占 Program 92%，roots 趟内 99% 是 `await entry.Prepared`（0.171~0.179s 对墙钟，差值仅 **2ms**），发布/应用/依赖入队全部合计约 2ms —— 推翻 r53 §10 的推测。②**模块解析主导 Program**：resolve 求和在安静批 0.137~0.367s（典型 0.31s），是 parse+bind 求和（0.135~0.161s）的 **2.3 倍**，约占 Program 墙钟一半 = Total 的 8~9%；读文件 0.05s、package scope 0.014s 是零星项。③**加并发无效（否决）**：parse+resolve 同升 8/12 无改善（Program 0.149/0.159 对 0.145）；拆开后 parse 固定 4 只提 resolve 到 8/16，resolve **求和**反涨到 0.50/0.70s 而墙钟不动（争用形态）。④**解析成本弥散**：`ModuleAsync` 本体 ≈ resolve，`NodeModulesAsync` 8~20%、`RealPath` 4~6%，其余散在逐候选路径构造与 `Trace`/`Message` 即时参数；单点价值均 1~3ms（<Total 1.5%、<本机 2.4% 伪差地板）。⑤**处置**：Program 轴关闭（产品代码零改动，探针 `phase:r55*` 与临时 `TSHARP_RESOLVE_CONCURRENCY` 均回退）。⑥**战役状态**：调度/缓存/并发/相位排列四类手段已无 ≥5% 可兑现空间（r43/r53/r55 同族）；要继续两位数收益只剩两条需用户裁决的路——与参考分叉的分区重平衡（r52 数据：checkPool 可降 0.13~0.29s，但跨会话翻转 + 分配 +6% + 基线失效），或表示层重写（紧凑类型对象/arena，tsrs 4~17× 的来源；表 2 的 arena 否决是「不建原型测不出局部性通道」的定价，非「已证无收益」）。
